Unidad 5 · Modelo relacional: claves e integridad

Descargar PDFVerificadores

Qué vas a poder hacer. Nombrar en una tabla sus atributos, dominios, grado y cardinalidad; encontrar sus superclaves y claves candidatas y elegir la primaria; declarar en SQL las claves foráneas y las restricciones (NOT NULL, UNIQUE, CHECK) para que la base rechace sola un dato imposible, y decidir qué les pasa a las filas hijas cuando se borra o se corrige la fila padre.

Lo que necesitas antes. La unidad 4: pasar un diagrama entidad-relación a tablas (una tabla por entidad, la clave foránea en el lado N de una relación 1:N y una tabla intermedia para una N:M). Saber leer un CREATE TABLE sencillo. Para correr los scripts basta Python, que trae el módulo sqlite3.

Tiempo. Unas 5 horas: 2 de lectura con los scripts abiertos y 3 de práctica.

Cómo están hechas las respuestas. Cada sentencia de esta unidad está en sql/u05_*.sql y la corre el verificador verificacion/u05_claves.py, una por una, en una base nueva. Las respuestas que ves («acepta», «rechaza» y el mensaje) son las que dio SQLite 3.50.4, la versión que trae Python 3.14. En MySQL el mensaje cambia de redacción, pero la regla que actúa es la misma; donde el comportamiento cambia, hay una nota.

1. La idea: que la base diga que no

Una base sin restricciones acepta todo: un préstamo de un libro que no existe, una nota 8,3, dos clientes con el mismo RUT. Si la regla vive solo en el programa que carga los datos, basta un segundo programa (una planilla importada, un script apurado, un practicante con acceso directo) para romperla.

Una restricción de integridad es una regla escrita una vez en el esquema que el motor hace cumplir a cualquiera que escriba. Hay tres familias:

Familia Qué protege Cómo se declara
Integridad de entidad que cada fila se pueda identificar PRIMARY KEY (única y no nula)
Integridad referencial que cada referencia apunte a algo que existe FOREIGN KEY ... REFERENCES
Integridad de dominio que cada valor sea posible tipo, NOT NULL, UNIQUE, CHECK, DEFAULT

La regla práctica que ordena toda la unidad: lo que el esquema no prohíbe, tarde o temprano pasa.

2. El vocabulario del modelo relacional

El modelo relacional (Codd, 1970) guarda todo en relaciones. Una relación es un conjunto de tuplas y se dibuja como una tabla.

Término formal En la tabla Ejemplo en la biblioteca de la sección 8
relación tabla socio
tupla fila (1, '15.432.876-9', 'Rosa Paillalef', 'Valdivia')
atributo columna rut
dominio conjunto de valores que puede tomar un atributo años entre 1450 y 2026 para anio
grado número de atributos socio tiene grado 4
cardinalidad número de tuplas en un momento dado socio tiene cardinalidad 4 al empezar
esquema la estructura: nombre, atributos y restricciones socio(id_socio, rut, nombre, comuna)
instancia (o estado) las filas que hay ahora las cuatro filas de la tabla

Notación. En el texto una tabla se escribe con su clave primaria en negrita y cada clave foránea con una flecha a la tabla que referencia:

  • socio(id_socio, rut, nombre, comuna)
  • prestamo(id_prestamo, id_ejemplar → ejemplar, id_socio → socio, salida, devolucion)

Tres propiedades de una relación. No tiene tuplas repetidas (es un conjunto); el orden de filas y columnas no significa nada; cada celda tiene un solo valor atómico. Una tabla de SQL sin clave primaria sí admite filas repetidas: es una bolsa, no un conjunto (ejercicio 5.1). La clave primaria es lo que la vuelve relación.

Cuidado con «cardinalidad». Acá es el número de filas de una tabla. En la unidad 3 era otra cosa: cuántas entidades se asocian con cuántas (1:1, 1:N, N:M). Mismo nombre, dos ideas.

El dominio es más que el tipo. anio INTEGER deja pasar 2062; el dominio real (años en que pudo editarse un libro) se escribe con un CHECK. El tipo es la primera aproximación del dominio y el CHECK lo termina de cerrar.

3. Claves

Sea \(R\) una relación con atributos \(A\). Para un subconjunto \(S \subseteq A\):

  • \(S\) es superclave si en ningún estado válido de \(R\) hay dos tuplas distintas que coincidan en todos los atributos de \(S\). El conjunto \(A\) entero siempre es superclave (no hay tuplas repetidas).
  • \(S\) es clave candidata si es superclave mínima: si le quitas cualquier atributo, deja de serlo.
  • La clave primaria es la candidata que eliges para identificar las filas. Las otras candidatas son claves alternativas y se declaran UNIQUE NOT NULL.
  • Un atributo es primo si pertenece a alguna clave candidata. La unidad 6 lo necesita.

Contar superclaves. Si \(R\) tiene grado \(n\) y una sola clave candidata \(K\), toda superclave es \(K\) más cualquier combinación de los otros \(n - |K|\) atributos:

\[\#\text{superclaves} = 2^{\,n-|K|}\]

Con dos claves candidatas \(K_1\) y \(K_2\) se suman las dos familias y se resta lo que se contó dos veces (las que contienen a ambas):

\[\#\text{superclaves} = 2^{\,n-|K_1|} + 2^{\,n-|K_2|} - 2^{\,n-|K_1 \cup K_2|}\]

En socio, de grado 4, las candidatas son {id_socio} y {rut}: \(2^3 + 2^3 - 2^2 = 12\), o sea, 12 superclaves. El verificador lo comprueba listando los 15 subconjuntos no vacíos de atributos. La fórmula no sirve para encontrar claves; sirve para darse cuenta de que «superclave» es un concepto amplio y «clave candidata» uno estrecho.

La clave sale de la regla, no de los datos. Que hoy ningún nombre se repita no hace del nombre una clave: mañana llega otra Carolina Muñoz. Los datos pueden refutar una clave (si hay dos filas iguales en \(S\), \(S\) no es superclave), pero nunca probarla. La pregunta correcta es «¿puede, según el negocio, haber dos filas con lo mismo en \(S\)?» (ejercicio 5.6).

Cómo se elige la primaria. Entre las candidatas, la que nunca es nula, nunca cambia, es corta y no carga significado que pueda quedar obsoleto. Muchas veces ninguna candidata natural cumple las cuatro, y se agrega una clave subrogada (sección 7).

Clave compuesta. Una tabla intermedia de una relación N:M (por ejemplo, telefono_socio o detalle_pedido del caso) tiene como clave el par de foráneas: la misma combinación no puede aparecer dos veces.

4. Integridad de entidad

La clave primaria no se repite y ningún atributo de la clave primaria es nulo: una fila que no se puede identificar no se puede referenciar, corregir ni borrar con certeza.

  • En SQL estándar y en MySQL, PRIMARY KEY implica NOT NULL.
  • En SQLite no siempre. Por compatibilidad con versiones antiguas, una clave primaria que no es INTEGER PRIMARY KEY admite NULL si no se le escribe NOT NULL. Por eso en esta unidad todas las claves de texto se declaran NOT NULL PRIMARY KEY (el ejercicio 5.10 muestra el problema).
  • INTEGER PRIMARY KEY en SQLite es un alias del número de fila: si insertas NULL o no la nombras, la base asigna el siguiente número. En MySQL eso se escribe INT AUTO_INCREMENT PRIMARY KEY; en SQL estándar, INTEGER GENERATED ALWAYS AS IDENTITY.

5. Integridad referencial

Una clave foránea es un atributo (o conjunto) de la tabla hija cuyos valores tienen que existir como clave primaria (o alternativa) en la tabla padre. La regla: todo valor no nulo de la foránea coincide con una clave del padre. Si la foránea admite NULL, la fila puede no apuntar a nadie; si es NOT NULL, la participación es obligatoria.

Va en el lado N: cada préstamo tiene un socio, así que id_socio está en prestamo y no al revés. Si se pusiera id_prestamo en socio, un socio podría tener un solo préstamo.

Se escribe aparte, con la columna entre paréntesis:

FOREIGN KEY (columna_hija) REFERENCES padre (columna_padre) ON DELETE accion ON UPDATE accion

Qué puede romperla. Insertar o modificar una fila hija con una foránea que no existe: siempre se rechaza. Borrar o cambiar la clave de una fila padre que tiene hijos: depende de la acción que se declaró.

Acción Qué hace al borrar (o cambiar) el padre Cuándo usarla
NO ACTION (la que rige si no escribes nada) rechaza si quedan hijos huérfanos por defecto
RESTRICT rechaza, y lo revisa de inmediato el hijo es historia que hay que conservar (un préstamo, un pedido)
CASCADE borra (o actualiza) también a los hijos el hijo no tiene sentido sin el padre (los teléfonos de un socio, el detalle de un pedido)
SET NULL deja la foránea de los hijos en NULL el hijo sobrevive y el vínculo era opcional; la columna tiene que admitir NULL
SET DEFAULT pone el valor por defecto rara vez: una categoría «sin asignar»

La pregunta para elegir: ¿el hijo tiene sentido sin su padre? No: CASCADE. Sí y es historia: RESTRICT, y el padre se marca como inactivo en vez de borrarse. Sí y el vínculo es opcional: SET NULL. ON UPDATE CASCADE sirve cuando la clave del padre es natural y puede corregirse (un ISBN mal digitado).

Notas de SQLite.

  • Las claves foráneas están apagadas por defecto y se encienden por conexión con PRAGMA foreign_keys = ON;. Sin esa línea, SQLite acepta huérfanos sin aviso (intento i10 del ejemplo). PRAGMA foreign_key_check; lista los que ya entraron.
  • NO ACTION revisa al terminar la sentencia; RESTRICT, en el momento. La diferencia se nota solo con restricciones diferidas o sentencias que dejan un huérfano y lo arreglan en el mismo paso.

Notas de MySQL.

  • Con InnoDB las foráneas se aplican siempre; NO ACTION y RESTRICT son lo mismo.
  • En MySQL 8.0, una foránea escrita dentro de la columna (id_tienda INTEGER REFERENCES tienda(id_tienda)) se lee y se ignora sin aviso: no crea la restricción. El manual lo dice así: «MySQL parses but ignores inline REFERENCES specifications». Las versiones 9 recientes ya la aceptan. Escríbela siempre aparte, con FOREIGN KEY (...). El esquema del caso de Estampa Sur usa la forma en línea: corre bien en SQLite y en MySQL 8.0 quedaría sin foráneas (sección 12).

6. Integridad de dominio: tipo, NOT NULL, UNIQUE, CHECK, DEFAULT

  • NOT NULL obliga a que haya un valor. Es una restricción aparte porque un CHECK deja pasar el NULL: la condición nota BETWEEN 1.0 AND 7.0 con nota nula no es falsa sino desconocida, y SQL solo rechaza lo falso. Si el valor es obligatorio, se escriben las dos.
  • UNIQUE impide repetir un valor (o una combinación). Admite varias filas con NULL, porque dos nulos no se consideran iguales. Una clave alternativa es UNIQUE NOT NULL.
  • CHECK (condición) limita el dominio: rangos, listas cerradas (IN (...)) y comparaciones entre columnas de la misma fila (devolucion >= salida). Con nombre (CONSTRAINT ck_anio CHECK (...)), el mensaje de error dice qué regla falló.
  • DEFAULT pone un valor cuando el INSERT no lo trae.

SQLite es flexible con los tipos, y eso es un riesgo. VARCHAR(12) no limita el largo; una columna INTEGER o REAL guarda un texto que no parece número como texto, y en SQLite un texto es mayor que cualquier número, así que CHECK (nota > 0) deja pasar 'seis' (ejercicio 5.8). Las defensas: una tabla STRICT (desde SQLite 3.37), que exige el tipo declarado, o un CHECK (typeof(nota) = 'real'). MySQL en modo estricto (el predeterminado desde la versión 5.7) rechaza el texto y el exceso de largo; sus CHECK se aplican desde la versión 8.0.16 (antes se leían y se ignoraban).

7. Clave natural o clave subrogada

Una clave natural sale del mundo: el RUT, la patente, el ISBN, el código pegado en una bicicleta. Una clave subrogada es un número sin significado que inventa la base (id_socio).

Natural Subrogada
Significado se entiende sola no dice nada; hay que hacer un join para saber quién es
Estabilidad puede corregirse o cambiar de formato no cambia nunca
Se repite en cada tabla hija sí, y con ella el dato personal solo el número
Duplicados del mundo real la base los impide hay que agregar un UNIQUE sobre la natural
Casos sin valor un extranjero sin RUT, un libro sin ISBN no existen

La regla de esta unidad: clave subrogada como primaria y la natural como clave alternativa (UNIQUE NOT NULL). La natural queda protegida contra duplicados y, si hay que corregirla, se cambia en una sola fila. Una natural sirve como primaria cuando es corta, estable y la controlas tú (el código de inventario PV-014 del ejercicio 5.5).

Con el RUT hay una razón más. Desde el 01-12-2026 rige la Ley 21.719 de protección de datos personales: un RUT usado como clave primaria se copia en cada tabla hija y en cada respaldo. Con una subrogada, el dato personal vive en una sola fila (ejercicio 5.7).

8. Ejemplo resuelto · La biblioteca vecinal de Valdivia

Una biblioteca vecinal presta libros a sus socios. Las reglas, dichas por la bibliotecaria:

  1. Cada socio tiene un RUT que no se repite, un nombre y una comuna; puede dejar varios teléfonos.
  2. Un libro se identifica por su ISBN y tiene uno o más ejemplares; cada ejemplar está disponible, prestado o dado de baja.
  3. Un préstamo es de un ejemplar a un socio, con fecha de salida y, cuando vuelve, de devolución, que no puede ser anterior a la salida.
  4. Un libro que tiene ejemplares no se borra del catálogo. Un ISBN mal digitado se corrige.
  5. Si un socio pide que borren sus datos, sus teléfonos se van con él; sus préstamos quedan para la estadística, sin decir de quién eran.

Paso 4 · El script (sql/u05_biblioteca.sql; la carga de datos está en el archivo):

-- Unidad 5 · Ejemplo resuelto · biblioteca vecinal de Valdivia (datos inventados)
-- Corre en SQLite (sqlite3 de Python) y en MySQL 8 (ver las notas de la unidad).
-- Las líneas «-- @nombre» marcan los intentos que el verificador muestra con su respuesta.
PRAGMA foreign_keys = ON;

CREATE TABLE socio (
    id_socio   INTEGER PRIMARY KEY,
    rut        VARCHAR(12) NOT NULL UNIQUE,
    nombre     VARCHAR(60) NOT NULL,
    comuna     VARCHAR(40) NOT NULL DEFAULT 'Valdivia'
);
CREATE TABLE telefono_socio (
    id_socio   INTEGER NOT NULL,
    telefono   VARCHAR(16) NOT NULL,
    PRIMARY KEY (id_socio, telefono),
    FOREIGN KEY (id_socio) REFERENCES socio (id_socio) ON DELETE CASCADE
);
CREATE TABLE libro (
    isbn       VARCHAR(17) NOT NULL PRIMARY KEY,
    titulo     VARCHAR(80) NOT NULL,
    anio       INTEGER NOT NULL CONSTRAINT ck_anio CHECK (anio BETWEEN 1450 AND 2026)
);
CREATE TABLE ejemplar (
    id_ejemplar INTEGER PRIMARY KEY,
    isbn        VARCHAR(17) NOT NULL,
    estado      VARCHAR(12) NOT NULL DEFAULT 'disponible'
                CONSTRAINT ck_estado CHECK (estado IN ('disponible', 'prestado', 'baja')),
    FOREIGN KEY (isbn) REFERENCES libro (isbn) ON DELETE RESTRICT ON UPDATE CASCADE
);
CREATE TABLE prestamo (
    id_prestamo INTEGER PRIMARY KEY,
    id_ejemplar INTEGER NOT NULL,
    id_socio    INTEGER,
    salida      DATE NOT NULL,
    devolucion  DATE,
    CONSTRAINT ck_fechas CHECK (devolucion >= salida),
    FOREIGN KEY (id_ejemplar) REFERENCES ejemplar (id_ejemplar) ON DELETE RESTRICT,
    FOREIGN KEY (id_socio) REFERENCES socio (id_socio) ON DELETE SET NULL
);

Cómo se lee.

  • Cada rechazo nombra la regla que actuó. Los CHECK con nombre (ck_anio, ck_fechas, ck_estado) dicen cuál falló; el UNIQUE y el NOT NULL dicen la columna. La foránea solo dice FOREIGN KEY constraint failed: en SQLite hay que deducir cuál de las foráneas fue.

9. Errores típicos

Error Cómo evitarlo
Olvidar PRAGMA foreign_keys = ON; en SQLite escríbelo como primera línea de cada conexión; revisa con PRAGMA foreign_key_check;
La foránea en el lado equivocado (id_prestamo en socio) la foránea va en el lado N: «cada préstamo tiene un socio» la pone en prestamo
Una relación N:M en una columna de texto ('joyas, cerámica') tabla intermedia con las dos foráneas como clave compuesta
Tabla intermedia sin clave primaria PRIMARY KEY (foránea_1, foránea_2): sin ella, la misma pareja entra dos veces
Creer que un CHECK impide el NULL el CHECK deja pasar lo desconocido; si el valor es obligatorio, agrega NOT NULL
Clave primaria de texto sin NOT NULL en SQLite escribe NOT NULL PRIMARY KEY; SQLite acepta NULL en esa clave por compatibilidad
Elegir una clave porque «hoy no se repite» la clave sale de la regla del negocio; los datos solo pueden refutarla
CASCADE en todas partes pregunta si el hijo es historia; un borrado en cascada puede arrastrar filas de otros (ejercicio 5.9)
SET NULL sobre una columna NOT NULL el error aparece recién al borrar el padre; decide si la columna es opcional
Foránea escrita en la columna en MySQL 8.0 escríbela aparte: FOREIGN KEY (col) REFERENCES padre (col), con paréntesis
Confiar en VARCHAR(n) e INTEGER en SQLite tabla STRICT o CHECK (typeof(...)); MySQL estricto sí los hace cumplir

-- Unidad 5 · Caso integrador · propuesta de restricciones para Estampa Sur
-- Se corre sobre OTRA copia de datos/estampa_sur.db. SQLite no cambia una restricción con ALTER TABLE:
-- la tabla se rehace (crear la nueva, copiar las filas, borrar la vieja y renombrar la nueva).
-- En MySQL basta ALTER TABLE ... DROP FOREIGN KEY y ADD CONSTRAINT.
PRAGMA foreign_keys = ON;

CREATE TABLE detalle_nuevo (
    id_pedido   INTEGER NOT NULL,
    id_producto INTEGER NOT NULL,
    cantidad    INTEGER NOT NULL CHECK (cantidad > 0),
    precio_unit INTEGER NOT NULL CHECK (precio_unit > 0),
    PRIMARY KEY (id_pedido, id_producto),
    FOREIGN KEY (id_pedido) REFERENCES pedido (id_pedido) ON DELETE CASCADE,
    FOREIGN KEY (id_producto) REFERENCES producto (id_producto) ON DELETE RESTRICT
);
INSERT INTO detalle_nuevo SELECT * FROM detalle_pedido;
DROP TABLE detalle_pedido;
ALTER TABLE detalle_nuevo RENAME TO detalle_pedido;

CREATE TABLE orden_nueva (
    id_orden    INTEGER PRIMARY KEY,
    id_producto INTEGER NOT NULL,
    semana      INTEGER NOT NULL CHECK (semana BETWEEN 1 AND 52),
    lote        INTEGER NOT NULL CHECK (lote > 0),
    UNIQUE (id_producto, semana),
    FOREIGN KEY (id_producto) REFERENCES producto (id_producto) ON DELETE RESTRICT
);
INSERT INTO orden_nueva SELECT * FROM orden_produccion;
DROP TABLE orden_produccion;
ALTER TABLE orden_nueva RENAME TO orden_produccion;

El orden de los pasos importa: con PRAGMA foreign_keys = ON, un DROP TABLE sobre una tabla padre hace un borrado implícito de sus filas y, si los hijos tienen CASCADE, se los lleva.
