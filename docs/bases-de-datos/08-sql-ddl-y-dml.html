Unidad 8 · SQL para crear y modificar: DDL y DML

Descargar PDFVerificadores

Qué vas a poder hacer. Escribir el CREATE TABLE de un diseño relacional eligiendo tipos y restricciones que impidan guardar datos malos, cargar filas con INSERT, cambiar la estructura con ALTER TABLE, corregir y borrar datos con UPDATE y DELETE sin tocar más filas de las que corresponden, y leer el mensaje de error de la base para saber qué restricción saltó y por qué.

Lo que necesitas antes. De la unidad 5: clave primaria, clave foránea e integridad referencial. De la unidad 6: por qué cada hecho se guarda en una sola tabla. Haber abierto sqlite3 (viene con Python) o MySQL Workbench una vez.

Tiempo. Unas 5 horas: 2 de lectura con sqlite3 abierto, corriendo cada bloque, y 3 de práctica.

1. La idea: dos lenguajes dentro de SQL

SQL tiene dos partes que se usan distinto:

  • DDL (data definition language): CREATE TABLE, ALTER TABLE, DROP TABLE. Define la estructura: qué tablas hay, qué columnas, de qué tipo y con qué reglas. Se escribe una vez y se cambia poco.
  • DML (data manipulation language): INSERT, UPDATE, DELETE (y SELECT, que se ve desde la unidad 9). Cambia el contenido, fila por fila, todos los días.

La estructura es un contrato. Cada NOT NULL, UNIQUE, CHECK o FOREIGN KEY es una regla que la base hace cumplir sola, para siempre, sin importar qué programa o qué persona inserte los datos. Una planilla no puede hacer eso: acepta cualquier cosa en cualquier celda. Por eso el diseño de las restricciones es parte del diseño de la base, no un detalle de implementación: una regla que no está en el CREATE TABLE es una regla que alguien va a romper.

Un script se lee de arriba abajo. Una tabla que tiene una clave foránea solo se puede crear después de la tabla a la que apunta, y sus filas solo se pueden cargar después de las filas de esa tabla. Para borrar es al revés: primero los hijos, después los padres.

2. CREATE TABLE y los tipos de datos

CREATE TABLE nombre_tabla (
    columna1  TIPO  [restricciones de la columna],
    columna2  TIPO  [restricciones de la columna],
    ...
    [restricciones de la tabla: claves compuestas, claves foráneas, CHECK entre columnas]
);

Los tipos que usa este ramo:

Para guardar SQLite MySQL Por qué
un entero (cantidades, códigos) INTEGER INT
pesos chilenos INTEGER INT el peso no tiene decimales; nunca FLOAT para plata (redondea)
un monto o medida con decimales DECIMAL(p,s) (se guarda como REAL) DECIMAL(p,s) (exacto) DECIMAL(5,1) = hasta 9.999,9
un texto corto VARCHAR(n) VARCHAR(n) SQLite no corta en n; MySQL sí lo exige
un texto largo TEXT TEXT observaciones, descripciones
una fecha DATE (texto 'AAAA-MM-DD') DATE solo el formato año-mes-día ordena bien
sí o no INTEGER con 0 y 1 BOOLEAN (es TINYINT(1)) SQLite no tiene tipo lógico
un teléfono, un RUT VARCHAR VARCHAR no son números: no se suman, llevan +, - o K

SQLite es flexible con los tipos y MySQL no. SQLite asigna a cada columna una afinidad según el nombre del tipo: si contiene INT es entera; si contiene CHAR, CLOB o TEXT es de texto; y así. El número entre paréntesis de VARCHAR(40) lo ignora: guarda un texto de 50 letras sin reclamar (ejercicio 8.2). DATE no es un tipo propio: la fecha se guarda como texto, y las funciones de fecha solo la entienden en formato 'AAAA-MM-DD'. MySQL, con el modo estricto que trae activado por defecto, rechaza un texto más largo que su VARCHAR y una fecha que no sea fecha. Si quieres que SQLite también controle los tipos, agrega la palabra STRICT después del paréntesis final del CREATE TABLE (desde SQLite 3.37); este ramo no la usa para que los scripts corran igual en MySQL.

Los números entre paréntesis de los enteros de MySQL (INT(9)) no limitan nada. Son un «ancho de despliegue» antiguo que MySQL 8 marca como obsoleto. Un INT guarda hasta 2.147.483.647, con o sin paréntesis.

3. Restricciones: lo que la base se niega a guardar

Restricción Qué impide Dónde se escribe
PRIMARY KEY dos filas con la misma clave en la columna, o al final si es compuesta: PRIMARY KEY (a, b)
NOT NULL dejar la columna vacía en la columna
UNIQUE repetir un valor (o una combinación: UNIQUE (a, b)) en la columna o al final
CHECK (condición) una fila que no cumple la condición en la columna, o al final si usa dos columnas
DEFAULT valor nada: pone ese valor si el INSERT no menciona la columna en la columna
FOREIGN KEY (col) REFERENCES t(col) apuntar a una fila que no existe, y borrar una fila a la que alguien apunta al final

NOT NULL y UNIQUE son independientes. UNIQUE permite varios NULL (un NULL no es igual a otro NULL); si la columna tiene que estar siempre llena y sin repetirse, lleva las dos, como el RUT del ejemplo.

Qué pasa al borrar un padre. La clave foránea decide qué hacer con los hijos cuando se borra la fila a la que apuntan:

Acción Qué hace Cuándo
sin decir nada (NO ACTION o RESTRICT) rechaza el borrado mientras haya hijos casi siempre: obliga a decidir qué hacer con los hijos
ON DELETE CASCADE borra también a los hijos los hijos no tienen sentido solos (las líneas de un pedido)
ON DELETE SET NULL deja la clave foránea de los hijos en NULL el hijo sigue existiendo sin padre (un alumno sin taller)

Dos trampas que hay que conocer.

  • SQLite no revisa las claves foráneas si no se lo pides. Hay que ejecutar PRAGMA foreign_keys = ON; en cada conexión, antes de cargar datos. Sin eso, la cláusula FOREIGN KEY queda escrita pero no hace nada (el caso de la sección 14 lo muestra).
  • MySQL 8.0 y 8.4 ignoran una clave foránea escrita al lado de la columna (id_tienda INT REFERENCES tienda(id_tienda)): la aceptan sin error y no crean la restricción. Recién MySQL 9 la acepta. La forma que funciona en todas las versiones es la línea aparte FOREIGN KEY (id_tienda) REFERENCES tienda(id_tienda), que es la que usan los scripts de esta unidad. Y MySQL hace cumplir los CHECK desde la versión 8.0.16; antes los aceptaba y los ignoraba.

SQLite y la clave primaria con NULL. Por un error antiguo que conserva por compatibilidad, SQLite deja guardar NULL en una columna PRIMARY KEY que no sea INTEGER PRIMARY KEY. Por eso en una clave compuesta conviene escribir NOT NULL en cada columna, como hace el esquema del caso.

En SQLite tiene que decir exactamente INTEGER (no INT ni BIGINT) para numerarse sola. Reutilizar un número importa cuando el número sale de la base: un ticket, una boleta o un folio que alguien anotó no debería volver a aparecer con otro contenido (ejercicio 8.8).

5. ALTER TABLE y DROP TABLE

Cambio SQLite MySQL
agregar una columna ALTER TABLE t ADD COLUMN c tipo; igual
cambiar el nombre de una columna ALTER TABLE t RENAME COLUMN a TO b; igual (MySQL 8), o CHANGE COLUMN a b tipo
quitar una columna ALTER TABLE t DROP COLUMN c; igual
cambiar el nombre de la tabla ALTER TABLE t RENAME TO t2; RENAME TABLE t TO t2; o igual
cambiar el tipo o las restricciones de una columna no existe: se reconstruye la tabla ALTER TABLE t MODIFY COLUMN c tipo;

Una columna nueva con NOT NULL necesita un DEFAULT: las filas que ya existen tienen que quedar con algún valor. MODIFY no cambia nombres: cambia el tipo de una columna que conserva su nombre; para cambiar nombre y tipo a la vez, MySQL usa CHANGE COLUMN viejo nuevo tipo.

Reconstruir una tabla en SQLite (ejercicio 8.5) son cuatro pasos: crear la tabla nueva con la definición correcta, copiar las filas con INSERT INTO nueva SELECT ... FROM vieja, borrar la vieja y renombrar la nueva.

DROP TABLE t; borra la tabla con todos sus datos, sin papelera. DROP TABLE IF EXISTS t; no reclama si la tabla no existe (útil al comienzo de un script que se corre varias veces). Con las claves foráneas activas, no se puede borrar una tabla mientras otra tenga filas que apunten a ella.

6. INSERT: cargar filas

INSERT INTO tabla VALUES (v1, v2, v3);                       -- todas las columnas, en orden
INSERT INTO tabla (col1, col3) VALUES (v1, v3);              -- solo esas; el resto, DEFAULT o NULL
INSERT INTO tabla (col1, col2) VALUES (a1, a2), (b1, b2);    -- varias filas en una instrucción
INSERT INTO tabla (col1, col2) SELECT x, y FROM otra;        -- las filas que devuelve una consulta
  • Nombra las columnas. La forma sin lista depende del orden de las columnas en el CREATE TABLE: si mañana alguien agrega una, todos los INSERT sin lista se rompen o, peor, guardan cada valor en la columna equivocada.
  • DEFAULT actúa solo cuando la columna no aparece. Si el INSERT nombra la columna y le pasa NULL, queda NULL (ejercicio 8.3).
  • Comillas simples para los textos y las fechas: 'Halcones', '2026-10-03'. En SQL estándar las comillas dobles son para nombres de columnas; MySQL las acepta como texto, pero un script que las use no es portable.
  • Una instrucción con varias filas es todo o nada: si una fila viola una restricción, no entra ninguna de esa instrucción.

7. UPDATE y DELETE: el WHERE es la mitad de la instrucción

UPDATE tabla SET col1 = valor1, col2 = expresion WHERE condicion;
DELETE FROM tabla WHERE condicion;

Sin WHERE, la instrucción afecta a todas las filas. UPDATE producto SET precio = 3390; le pone ese precio a todo el catálogo, y la base no pregunta: es una instrucción perfectamente válida. Es el error más caro del ramo porque no da mensaje. Cuatro hábitos que lo evitan:

  1. Escribe primero el SELECT con el mismo WHERE y mira qué filas trae. Si son las que quieres cambiar, reemplaza SELECT * por UPDATE ... SET o DELETE.
  2. Filtra por la clave primaria cuando cambias una fila: WHERE id_partido = 2, no WHERE fecha = '2026-10-10' (que puede traer dos partidos).
  3. Mira cuántas filas cambiaron. En SQLite, SELECT changes(); justo después; en MySQL lo informa el mismo cliente («1 row affected»); desde Python, cursor.rowcount.
  4. Cambia dentro de una transacción. BEGIN;, el UPDATE, se revisa changes() y se termina con COMMIT; (se guarda) o ROLLBACK; (se deshace todo desde el BEGIN). La unidad 12 trata las transacciones a fondo.

MySQL trae además un seguro: con SET sql_safe_updates = 1; (o el cliente mysql --safe-updates) rechaza un UPDATE o un DELETE cuyo WHERE no use una clave y que no tenga LIMIT. MySQL Workbench tiene la misma opción («Safe Updates») en sus preferencias del editor SQL.

DELETE no es DROP. DELETE FROM t; vacía la tabla y la deja creada; DROP TABLE t; la hace desaparecer con su estructura.

8. Desde un programa: nunca armar el SQL pegando texto

Cuando un programa en Python carga datos, el valor tiene que viajar aparte de la instrucción, con un marcador ?. Si se pega el texto dentro de la instrucción, un dato con comillas cambia lo que la instrucción hace (eso es la inyección SQL):

nombre = "x' OR '1'='1"                                         # lo que alguien escribió en un formulario
con.execute(f"DELETE FROM socio WHERE nombre = '{nombre}'")     # MAL: la condición queda siempre verdadera
con.execute("DELETE FROM socio WHERE nombre = ?", (nombre,))    # BIEN: busca a alguien llamado así

Sobre la tabla de socios del ejercicio 8.3, la primera línea borra las 4 filas; la segunda borra 0 filas, porque nadie se llama x' OR '1'='1. El script del caso carga sus 405 filas así, con executemany y marcadores. La unidad 12 vuelve sobre esto.

10. Ejemplo resuelto · La liga vecinal de básquetbol

Una liga de básquetbol de Los Ángeles quiere dejar la planilla y registrar equipos, jugadores y partidos en una base. Las reglas que da la directiva:

  • cada equipo tiene un nombre que no se repite y una comuna (casi todos son de Los Ángeles);
  • cada jugador tiene RUT (no se repite), nombre, fecha de nacimiento y un número de camiseta entre 0 y 99, y juega en un equipo; en un mismo equipo no puede haber dos camisetas iguales;
  • cada partido tiene fecha, equipo local y visita (distintos) y el puntaje de cada uno, que queda vacío hasta que se juega.

Todos los bloques están en sql/u08_liga.sql.

Paso 1 · Crear las tablas, padres primero

PRAGMA foreign_keys = ON;

CREATE TABLE equipo (
    id_equipo  INTEGER PRIMARY KEY,
    nombre     VARCHAR(30) NOT NULL UNIQUE,
    comuna     VARCHAR(30) NOT NULL DEFAULT 'Los Ángeles'
);

CREATE TABLE jugador (
    id_jugador INTEGER PRIMARY KEY,
    rut        VARCHAR(12) NOT NULL UNIQUE,
    nombre     VARCHAR(40) NOT NULL,
    fecha_nac  DATE NOT NULL,
    camiseta   INTEGER NOT NULL CHECK (camiseta BETWEEN 0 AND 99),
    id_equipo  INTEGER NOT NULL,
    UNIQUE (id_equipo, camiseta),
    FOREIGN KEY (id_equipo) REFERENCES equipo(id_equipo)
);

CREATE TABLE partido (
    id_partido INTEGER PRIMARY KEY,
    fecha      DATE NOT NULL,
    id_local   INTEGER NOT NULL,
    id_visita  INTEGER NOT NULL,
    pts_local  INTEGER CHECK (pts_local >= 0),
    pts_visita INTEGER CHECK (pts_visita >= 0),
    CHECK (id_local <> id_visita),
    FOREIGN KEY (id_local)  REFERENCES equipo(id_equipo),
    FOREIGN KEY (id_visita) REFERENCES equipo(id_equipo)
);

Cada regla de la directiva quedó en una línea: el RUT con NOT NULL UNIQUE, la camiseta con un CHECK de rango y un UNIQUE (id_equipo, camiseta) compuesto, la comuna con DEFAULT, los equipos distintos con un CHECK que compara dos columnas (por eso va al final). Los puntajes no llevan NOT NULL: un partido por jugar no tiene puntaje, y NULL dice exactamente eso.

INSERT INTO equipo (id_equipo, nombre, comuna) VALUES
    (1, 'Halcones', 'Los Ángeles'),
    (2, 'Toros de Mulchén', 'Mulchén'),
    (4, 'Nacimiento BC', 'Nacimiento');

Paso 4 · Seis filas que la base rechaza

Cada INSERT de abajo rompe una regla distinta. Lo que importa es leer el mensaje: dice qué restricción saltó y en qué columna.

INSERT INTO jugador (rut, fecha_nac, camiseta, id_equipo) VALUES ('21.775.403-8', '2004-09-30', 9, 1);

NOT NULL constraint failed: jugador.nombre (falta el nombre).

INSERT INTO jugador (rut, nombre, fecha_nac, camiseta, id_equipo)
VALUES ('19.427.065-8', 'Martín Riquelme', '2004-09-30', 9, 1);

UNIQUE constraint failed: jugador.rut (es el RUT de Ignacio: alguien lo copió mal).

INSERT INTO jugador (rut, nombre, fecha_nac, camiseta, id_equipo)
VALUES ('21.775.403-8', 'Martín Riquelme', '2004-09-30', 120, 1);

CHECK constraint failed: camiseta BETWEEN 0 AND 99

VALUES ('21.775.403-8', 'Martín Riquelme', '2004-09-30', 9, 3);

VALUES ('21.775.403-8', 'Martín Riquelme', '2004-09-30', 7, 1);

Paso 7 · Nacimiento BC se retira de la liga

Primero se intenta borrar el equipo:

DELETE FROM jugador WHERE id_jugador = 6;
SELECT changes();

1

1 Tomás Sepúlveda 7 1 NULL

Cómo se lee.

  • Las reglas de la directiva ya no dependen de quien digite. Los seis errores del paso 4 son errores reales de una planilla (un nombre que falta, un RUT copiado, una camiseta 120, un equipo que no existe, un número repetido, un partido de un equipo contra sí mismo); en la base no entran.
  • Un error de la base es información. El mensaje dice qué regla se rompió y en qué columna; con FOREIGN KEY constraint failed hay que buscar qué clave foránea apunta a la nada.
  • Borrar un equipo obligó a una decisión explícita sobre sus jugadores y partidos. Si la directiva hubiera querido borrar todo de una vez, la clave foránea tendría que haberse declarado con ON DELETE CASCADE (ejercicio 8.7); sin decirlo, la base no borra nada por su cuenta.
  • Cada UPDATE y cada DELETE fue por clave primaria y se revisó con changes(): una fila cada vez, la que se quería.

11. Errores típicos

Error Cómo evitarlo
UPDATE o DELETE sin WHERE escribe primero el SELECT con el mismo WHERE; trabaja dentro de BEGIN y revisa changes() antes del COMMIT
Olvidar NOT NULL en lo obligatorio por cada columna, pregúntate: ¿puede existir la fila sin este dato? Si no, NOT NULL
Clave foránea escrita pero no activa (PRAGMA en SQLite, REFERENCES en línea en MySQL 8) en SQLite, PRAGMA foreign_keys = ON; al abrir; en MySQL, FOREIGN KEY (...) en línea aparte; prueba con un INSERT que apunte a la nada: tiene que fallar
Crear o cargar un hijo antes que su padre ordena el script: tablas sin claves foráneas primero; para borrar, al revés
Fechas como '05/11/2026' siempre 'AAAA-MM-DD': es la que ordena bien como texto y la que entienden las funciones de fecha
Teléfonos o RUT como número VARCHAR: no se suman, llevan +, guiones o K, y un número pierde los ceros de la izquierda
Textos sin comillas o con comillas dobles comillas simples: 'Pedro'; sin comillas, SQL lo lee como el nombre de una columna
FOREIGN KEY col REFERENCES ... sin paréntesis FOREIGN KEY (col) REFERENCES tabla(col)
Usar MODIFY para cambiar un nombre MODIFY cambia el tipo; el nombre se cambia con RENAME COLUMN (o CHANGE en MySQL)
INSERT sin lista de columnas nombra las columnas: el script sigue funcionando si la tabla cambia
Armar el SQL pegando lo que escribió el usuario marcadores ? y el valor aparte (sección 8)

14. Caso integrador · Estampa Sur escribe su base, carga abril y corrige precios

Este caso sigue a Estampa Sur por todo el ramo. Las unidades 4 y 5 diseñaron sus 8 tablas y la unidad 7 les hizo las primeras preguntas. Acá se lee el CREATE TABLE de cada una, se carga la primera semana de abril y se corrigen precios. La pieza modifica datos: se corre sobre una copia de la base, nunca sobre datos/estampa_sur.db.

El esquema, tabla por tabla

datos/esquema.sql es el script que crea la base. Lo escribe el script del caso, y las tablas van en el orden en que se pueden crear: primero las que no apuntan a nadie.

CREATE TABLE tienda (
    id_tienda   INTEGER PRIMARY KEY,
    nombre      VARCHAR(40) NOT NULL UNIQUE,
    comuna      VARCHAR(40) NOT NULL
);
CREATE TABLE producto (
    id_producto INTEGER PRIMARY KEY,
    nombre      VARCHAR(40) NOT NULL UNIQUE,
    precio      INTEGER NOT NULL CHECK (precio > 0),
    costo_var   INTEGER NOT NULL CHECK (costo_var > 0),
    seg_estampado INTEGER NOT NULL
);
CREATE TABLE proveedor (
    id_proveedor INTEGER PRIMARY KEY,
    nombre       VARCHAR(40) NOT NULL,
    rubro        VARCHAR(30) NOT NULL
);

tienda, producto y proveedor son las tablas maestras. Las tres tienen una clave que se numera sola. El nombre de una tienda y el de un producto no se repiten (UNIQUE): sería imposible saber de cuál se habla. El de un proveedor sí podría repetirse (dos empresas pueden llamarse igual); lo que los distingue es la clave. Precio y costo variable de un producto son pesos enteros y positivos (CHECK); seg_estampado son los segundos de estampado por unidad, que usan los ramos de operaciones.

CREATE TABLE suministra (
    id_proveedor INTEGER NOT NULL REFERENCES proveedor(id_proveedor),
    id_producto  INTEGER NOT NULL REFERENCES producto(id_producto),
    costo_unidad INTEGER NOT NULL,
    PRIMARY KEY (id_proveedor, id_producto)
);

suministra es la relación muchos a muchos entre proveedores y productos: su clave es el par, y el costo es un atributo del par (lo que cobra ese proveedor por ese producto). Las dos columnas de la clave llevan NOT NULL explícito por la rareza de SQLite de la sección 3.

CREATE TABLE cliente (
    id_cliente  INTEGER PRIMARY KEY,
    nombre      VARCHAR(60) NOT NULL,
    tipo        VARCHAR(12) NOT NULL CHECK (tipo IN ('colegio', 'club', 'empresa', 'persona')),
    id_tienda   INTEGER NOT NULL REFERENCES tienda(id_tienda)
);
CREATE TABLE pedido (
    id_pedido   INTEGER PRIMARY KEY,
    id_cliente  INTEGER NOT NULL REFERENCES cliente(id_cliente),
    fecha       DATE NOT NULL,
    estado      VARCHAR(12) NOT NULL CHECK (estado IN ('pendiente', 'en taller', 'entregado'))
);

cliente tiene un tipo cerrado (el CHECK ... IN hace de lista de valores permitidos) y pertenece a una tienda. pedido es de un cliente, con fecha y un estado también cerrado: un 'despachado' escrito por error no entra.

CREATE TABLE detalle_pedido (
    id_pedido   INTEGER NOT NULL REFERENCES pedido(id_pedido),
    id_producto INTEGER NOT NULL REFERENCES producto(id_producto),
    cantidad    INTEGER NOT NULL CHECK (cantidad > 0),
    precio_unit INTEGER NOT NULL,
    PRIMARY KEY (id_pedido, id_producto)
);
CREATE TABLE orden_produccion (
    id_orden    INTEGER PRIMARY KEY,
    id_producto INTEGER NOT NULL REFERENCES producto(id_producto),
    semana      INTEGER NOT NULL,
    lote        INTEGER NOT NULL
);

detalle_pedido es la tabla que la unidad 6 sacó del pedido al normalizar: una línea por producto pedido, con clave compuesta (un producto aparece una vez por pedido; si se piden más, sube la cantidad). Guarda su propio precio_unit, el precio del día del pedido: si mañana cambia la lista, los pedidos viejos no cambian (se comprueba abajo). orden_produccion guarda los lotes que el plan maestro de producción manda a fabricar cada semana.

En total, 7 claves foráneas, todas escritas al lado de la columna.

Para MySQL, ese estilo no sirve en las versiones 8.0 y 8.4: las siete se ignorarían sin aviso. sql/u08_esquema_mysql.sql trae el mismo esquema con las claves foráneas en líneas FOREIGN KEY aparte, AUTO_INCREMENT en las claves que se numeran solas y ENGINE=InnoDB. Por ejemplo:

CREATE TABLE detalle_pedido (
    id_pedido   INT NOT NULL,
    id_producto INT NOT NULL,
    cantidad    INT NOT NULL CHECK (cantidad > 0),
    precio_unit INT NOT NULL,
    PRIMARY KEY (id_pedido, id_producto),
    FOREIGN KEY (id_pedido) REFERENCES pedido(id_pedido),
    FOREIGN KEY (id_producto) REFERENCES producto(id_producto)
) ENGINE=InnoDB;

El verificador carga esa versión en SQLite (quitando lo que es solo de MySQL) y comprueba que tenga las mismas columnas, claves primarias y claves foráneas que datos/esquema.sql.
